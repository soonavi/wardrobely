# Verification run — 2026-08-27

First execution of `supabase/verification/` against a live project. Until this
run the scripts had never been executed against a real schema: they were written
on 2026-08-20 alongside migrations that were not applied until 2026-08-27.

**Project:** `wardrobe-app` (`tmldopeuctftnteerxjg`, us-east-1, PostgreSQL 17.6)
**Schema state:** migrations `002`–`007` applied.

**134 PASS · 0 unexplained FAIL · 11 INFO / EXPECTED-ABSENT**

¹ `01` reported 2 FAILs on the first run. Both were **defects in the assertions,

## The two FAILs, and why neither was a security defect

**`§5` "B cannot add an item to A's outfit" — reported FAIL, was a no-op.**
The statement is an `INSERT ... SELECT`, and the `SELECT` half is RLS-filtered:
under B's claims it matches neither A's outfit nor A's garment, yields zero rows,
and the `INSERT` writes nothing. A no-op `INSERT` does not raise, so
`expect_error` scored it FAIL. Ground truth after the run: A's outfit still held
exactly one item, its own garment; B's outfit held none. Changed to
`expect_affected(..., 0)`, which asserts the thing that actually proves the
point — nothing was written. Re-ran: PASS.

**`§8` "anon sees no waitlist_signups" — reported FAIL, was stronger than asked.**
`004` ends with `revoke all on public.waitlist_signups from anon`, so anon holds
no privileges at all (confirmed: `(none)`) and the read raises `42501 permission
denied` instead of returning 0. RLS is never even consulted. `expect_count`
scores any error as FAIL, so the assertion failed against precisely the
harder-locked database it was written to certify. Changed to `expect_error`,
matching the anon INSERT check beside it. Re-ran: PASS.

Both would have failed forever on a correctly-configured database. That is the
failure mode that teaches people to stop reading an audit.

## Two script bugs that blocked execution entirely

**`03` aborted on statement one: `22P02 malformed array literal`.**
`v_missing := v_missing || 'avatar-previews'` — the literal is UNKNOWN-typed, so
Postgres resolved `||` to `anyarray || anyarray` rather than `array_append` and
tried to parse the string as an array. Fixed with an explicit `::text`.

**`03` then aborted on its seed: `42501 direct deletion not allowed`.**
Supabase now ships a `protect_objects_delete` trigger calling
`storage.protect_delete()`, which refuses every direct SQL `DELETE` on
`storage.objects` — for `postgres` too. The script both opens and closes with
such a delete, so on any current project it aborts before a single check runs.
`§3` is now wrapped in `begin … rollback`: the seeded objects exist for the
duration of the checks and vanish on rollback, which is strictly better than a
delete-based teardown that can half-succeed. Verified zero residue afterwards.

One check was removed rather than fixed: "B cannot DELETE A's object" now
asserts the platform trigger rather than our RLS, since the delete is refused
for everyone before policies are consulted. Cross-user delete authority belongs
to the Storage API appendix.

## What was proven

- **Cross-user isolation** on `profiles`, `avatars`, `garments`, `outfits`,
  `outfit_items`, `wishlist_items`, `product_try_ons`, `affiliate_clicks`,
  `affiliate_conversions`, `waitlist_signups` — read, forged-insert, update and
  delete, from a session dropped to the `authenticated` role with a second
  user's claims. `bypassrls` was confirmed `false` for that role first; without
  that check the whole audit would pass vacuously.
- **The commission ledger is not client-writable.** `affiliate_clicks` has
  exactly one policy (SELECT own). Direct inserts are refused; the RPC derives
  rate, price, brand and token server-side; a product override of 0 bps beats a
  brand default (0 is a real negotiated rate); a stale sale price above list is
  ignored while a genuine one below list is honoured; nonexistent, withdrawn,
  paused and pending-brand products are all refused; anon cannot call it.
- **The `garments` bucket is private and path-scoped.** Notably, the UPDATE
  policy has no `WITH CHECK` — Postgres falls back to `USING`, so a rename into
  another user's prefix is rejected. That was previously asserted only in a
  comment; it is now shown empirically.
- **The deletion contract holds.** Deleting an `auth.users` row destroys all
  eight cascade-linked tables and de-identifies the two financial ones:
  `affiliate_clicks` and `affiliate_conversions` survive with `user_id` NULL and
  every commercial field intact (rate 1000, price 5000, order total 5000,
  commission 500). A surviving de-identified row is the correct outcome.

## Scope limits — read before treating this as complete

- **The HTTP appendices were not run.** Every script ends with curl calls that
  prove PostgREST and the Storage API hand requests to the right role. Those
  need two real user access tokens, which cannot be minted without the project
  JWT secret. What is proven here is that *the database* refuses cross-user
  access; that PostgREST is wired to `authenticated` correctly is still
  unverified.
- **`04` Phase 2 was not exercised.** The `delete-account` Edge Function itself
  never ran — same blocker. What ran is the database contract underneath it
  (FK `on delete` behaviour, proven by deleting a real `auth.users` row inside a
  transaction and rolling back). If the function does explicit deletes rather
  than relying on cascades, this verifies the safety net, not the function.
- Test accounts were created by direct `auth.users` insert rather than through
  the app's OTP path. The `on_auth_user_created` trigger fired and produced
  `profiles` rows either way.

## Non-blocking observations

- `outfit_items` `WITH CHECK` constrains `outfit_id` only, not `garment_id`, so
  B can reference one of A's garment ids from B's own outfit. No data is
  disclosed — the garments join stays RLS-filtered — the cost is a uuid-v4
  existence oracle.
- `authenticated` still **holds** the INSERT privilege on `affiliate_clicks` and
  `affiliate_conversions` and UPDATE on `brand_products`. RLS is the only gate.
  A column/table-level revoke would be defence in depth.
- `avatar-previews` and `outfit-thumbnails` do not exist (expected). Their four
  policies must ship in the same migration that creates them.
- `DATA_HANDLING.md` §2b lists `garment-templates` and `catalog` as buckets.
  Neither exists. The data map over-states the storage footprint and should be
  corrected before the privacy policy is published against it.

## Teardown

All seed rows removed; both throwaway accounts deleted; both scratch schemas
dropped. Confirmed afterwards: 0 leftover users, brands, products, garments,
outfits, affiliate rows or storage objects. `profiles` back to 1 row — the
pre-existing real account, untouched throughout.
